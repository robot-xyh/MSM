# 正式分片压缩归档验证

## 结论

正式实验分片已经具备确定性压缩、完整性复核和规范路径恢复能力。工具按文件冻结摘要，
同时绑定执行计划、父计划、源提交和分片编号。压缩和恢复均不修改历史源目录，也不提供
自动删除入口。

归档工具现已增加低峰值范围合并。完整归档集合形成后，工具按 execution plan 顺序逐片
验证和临时恢复，每次只保留一个恢复分片。范围表和 D6 派生结果在全部 20 片通过后原子
发布，不再要求 20 个原始分片同时驻留。该入口已经通过开发夹具，尚未用于完整正式 R0。

2026 年 7 月 31 日使用历史完整分片 17 进行非破坏性验证。原始分片包含 1850 个文件，
总大小 1,086,483,308 字节。压缩包大小为 113,628,123 字节，占原始大小的 10.46%。
恢复后的文件树摘要与原始分片一致。该结果说明逐片压缩可以降低新一轮 900 单元实验的
驻留空间，但不构成删除历史证据的授权。

## 归档合同

每个归档目录固定包含三个文件：

- `shard_payload.tar.zst`：固定顺序、固定时间、固定权限和固定属主的压缩载荷；
- `shard_archive_manifest.json`：执行绑定、文件清单、树摘要和压缩参数；
- `SHA256SUMS`：manifest 与压缩载荷的 SHA-256。

创建归档前，工具调用分片存储校验。该校验复用确定性合并路径的主要检查项：

1. `shard_plan.json` 必须与 execution plan 的分片描述和单元清单一致；
2. `progress.jsonl` 必须连续覆盖本分片全部单元；
3. 每个单元结果、episode 目录和文件树摘要必须有效；
4. `checkpoint.json` 必须标记完成，完成数和进度摘要必须一致；
5. 分片编号、父计划摘要、源提交和 execution plan 摘要必须匹配。

归档采用 PAX tar 和单线程 Zstandard。文件写入顺序来自排序后的冻结清单。时间戳设为
零，文件权限固定为 `0644`，用户和组编号固定为零。相同源、相同压缩级别和相同工具环境
生成相同的压缩载荷摘要。

## 安全处理

压缩前先计算逐文件清单和树摘要。压缩完成后，工具从压缩流重新读取全部文件并核对
大小和摘要，然后再次读取源目录。源目录在压缩期间发生变化时，临时归档被丢弃，正式
归档目录不会发布。

恢复只允许普通文件和规范相对路径。绝对路径、上级目录跳转、反斜杠路径、重复文件、
符号链接、硬链接和设备文件均被拒绝。文件先写入临时恢复目录。完整清单通过后再原子
发布到 execution plan 对应的规范分片目录，并再次执行分片语义校验。

`source_deletion_eligible=true` 只表示本次复核时源和归档相等。工具不会删除源目录。
原始分片的移除必须由运行负责人另行确认，并保留归档 manifest、SHA-256 和复核结果。

## 归档原生合并

`merge-archives` 先核对归档子目录集合。缺片、额外目录和符号链接直接失败；pack/verify
结果 JSON 属于旁路记录，不作为归档目录。每个归档随后重新检查 manifest、SHA256SUMS、
压缩载荷和 execution plan 绑定。载荷恢复到隔离临时执行根，继续执行普通 shard 的
计划、进度、checkpoint、单元结果、episode 和文件树检查。

临时 episode 仍存在时，D6 逐单元生成预评估行。该分片完成后，临时目录在下一片恢复前
释放。最终输出只保存范围 manifest、单元表、逻辑 episode 索引、归档摘要和 D6 报告；
manifest 明确标记规范 episode 目录没有 materialize。D6 报告 binding 记录评估器版本、
源码摘要以及各报告文件的路径、大小和 SHA-256。

开发测试覆盖规范目录合并等价、旁路结果文件、缺片、额外目录、压缩损坏、容量保护、
staging 与输出重叠、命令行和源目录释放后的 D6 报告。归档专项为 `15 passed`，三维规模化
模块全量为 `431 passed`。警告来自本机 Matplotlib 三维投影环境。

对 clean `80e55eb` 正式目录执行了非破坏性预检。当前只有 shard 0-9，工具明确报告
缺少 shard 10-19，额外归档目录为空。merge 输出和 staging 目录均未创建，任何归档和
原始分片均未修改。

D6 已增加独立归档审计，不调用 main 的 verified 结果。审计器复算每片校验和、清单、
压缩载荷、执行计划绑定和 tar 成员，并在一次一片的临时目录中复用低层后验。随后独立
检查 merge 分片索引、单元数、逻辑路径、报告 provenance 和五类报告摘要。专项测试为
`32 passed`，D6 全量为 `1297 passed`。main 与 D6 的实际开发夹具已验证 sidecar、归档
摘要和 `sha256:<64位摘要>` 格式一致。

本轮实现提交分别为 main 归档合并 `84e1cf5` 和 D6 独立审计 `cf00581`。正式运行仍须
记录完整提交号、工作树 clean 状态和 execution plan SHA-256。

正式 10/20 D6 预检接受归档根中的 20 个 pack/verify sidecar，只因缺少 shard 10-19
失败关闭。`verified_archive_count`、R0 completed 分母和 parent completed 分母均为 0，
未解压任何分片，也未生成 merge 输出。

## 正式执行

正式 R0 继续使用 20 个分片，每片 45 个单元。推荐顺序如下：

1. 在新的干净提交上初始化 900 单元 execution plan；
2. 运行一个分片，保持 20 GiB 可用空间保护线；
3. 对完成分片执行压缩并保存结果 JSON；
4. 使用 `verify-shard --source` 再次复核源和归档；
5. 经明确授权后，人工移除该分片的原始目录；
6. 重复处理后续分片；
7. 补齐 20 个归档目录后执行 `merge-archives --write-d6-report`；
8. 工具逐片临时恢复、复核并原子发布范围结果，不要求全部原始分片同时存在；
9. 由 D6 独立复核归档、范围合并和报告 binding，再对 900 个单元开展正式后验审计。

当前 clean `80e55eb` 已完成 450/900。尚未获得移除 shard 0-9 原始目录或继续运行
shard 10-19 的授权，现有原始目录和归档保持原状。
