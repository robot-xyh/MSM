# 高威胁多机协同时期租约开发复验

## 结论

本轮补齐了 D3 权威计划与 D4 降级执行之间的时期和租约发布合同。每个新的
`plan_id + plan_version` 在首次权威发布前绑定一次不可变
`authority_epoch` 和 `lease_expires_at_s`，并同时发布区域最大时期和最小租约。
同身份评价刷新只更新诊断，不生成第二份权威载荷，也不延长租约。

开发工作树上的 100 组 `high_threat_m_to_n` 复验全部保持有限状态和在线真值隔离。
D6 直接读取落盘制品，确认最终 D3-D4 计划、时期、租约和联盟状态均为
`100/100` 可用且匹配。v4 中时期和租约均为 `0/100 available` 的 P1 已在开发证据
层关闭。

该批次来自脏工作树，100 个 manifest 均为 `repository_dirty=true`。结果只能用于
修复判断，不能标记为正式 R0，也不能替代 clean source 上的 900-cell 规范矩阵。

## 实现

### D3 绑定

D3 增加两级显式绑定。

`AssignmentPlan.bind_authority_generation()` 校验：

- 时期为非负整数；
- 租约有限且晚于计划创建时刻；
- 首次绑定保持原 `plan_id` 和 `plan_version`；
- 相同值重复调用为幂等操作；
- 同一计划身份修改时期或租约立即失败关闭。

`AssignmentPlanner.bind_published_authority_generation()` 同步更新规划器内部的已发布
计划、可信执行签名和规划上下文。该入口解决了后置绑定与下一轮 stale check 之间的
签名一致性问题。

新计划身份不得继承上一身份的通用时期和租约。D3 已分别处理普通执行语义变化、权限
代次 fence、二级节点接管与延续、区域后继计划和区域权限计划。同身份评价刷新保留
原绑定，即使评价发生在租约到期之后，也不得以刷新方式续租。

### main 接线

main 在每次 D3 规划结果进入 D4、D5 和 D7 前执行一次统一绑定：

1. 从当前计划权限语义计算时期；
2. 使用 D4 已有冻结租约函数取得该计划代次唯一截止时刻；
3. 调用 D3 planner 级绑定入口；
4. 以绑定后的计划替换 main 当前计划；
5. 再生成制导绑定、D4 快照和权威总线载荷。

权威发布入口强制检查以下四个字段：

- `authority_epoch`；
- `lease_expires_at_s`；
- `regional_max_epoch`；
- `regional_min_lease_expires_at_s`。

缺少任一字段时不发布，并增加权威载荷冲突诊断。首次传输摘要和总线序号仍保持不可变。

### D4 保持

D4 算法和执行门控没有放宽。无可执行后继的区域建议仍保持原计划身份，不产生新计划、
第二次权威发布或 adoption ACK。当前计划继续携带首次绑定的时期和租约，不因 no-op
评价刷新而续租。

二级接管、分布式接管、成员确认、网络分区和租约到期仍按原规则失败关闭。D7 仍要求
当前 D2 航迹、身份承诺、当前计划和完整联盟，不能仅依据 D4 缓存航迹获得控制权限。
