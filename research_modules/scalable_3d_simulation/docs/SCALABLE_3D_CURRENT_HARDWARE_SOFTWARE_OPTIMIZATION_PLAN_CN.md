# 当前硬件软件优化方案

## 当前基线

当前计算平台为 Intel Core Ultra 9 185H，约 16 核 22 线程，配套 RTX 4050 6GB
显卡。200 对 200 三维质点规则基线在持续 10 秒场景中的实际处理速度约为
2.3 帧/秒，目标物理更新频率为 20 赫兹。

当前主要耗时集中在 D1 多传感器融合、扫描输入和历史重放。质点动力学、D3 分配和
D5 视觉配准不是现阶段的首要瓶颈。

| 阶段 | 目标速度 |
| --- | ---: |
| 当前基线 | 约 2.3 帧/秒 |
| 第一轮低风险优化 | 3.5～5 帧/秒 |
| D1 向量化和稀疏关联 | 6～9 帧/秒 |
| 并行化和局部本地内核 | 10～14 帧/秒 |
| 20 帧/秒实时运行 | 需要更深的本地编译和数据结构改造 |

## 性能基线

固定 200 对 200、10 秒和 3 个开发随机种子。关闭图片、动画和学习模型，保留完整规则
链路。每轮优化前后使用相同场景、相同随机种子和相同运行频率。

记录以下指标：

1. 核心墙钟时间和实时倍率；
2. D1 扫描、融合和历史重放的平均值、P50 和 P95；
3. D2 关联、D3 分配、D5 配准和 D7 导引耗时；
4. 候选对、矩阵求解、历史重放和航迹物化次数；
5. 峰值内存、运行时数据复制量和日志写入量；
6. 业务记录规范摘要及最终模块状态。

每轮采用交错 A/B 重复运行，降低笔记本温度、功耗和动态频率对测量结果的影响。

## 低风险优化

### 影子旁路离线化

A2 共同质心影子旁路继续默认关闭。规则基线运行时不计算完整影子摘要。需要审计时，
从持久化规范航迹快照离线执行。

该调整不改变规则算法，但可避免影子模式额外约 80.88% 的运行开销。

### 延迟日志序列化

在线总线保留结构化对象、版本号和必要摘要，episode 结束后再转换为 JSONL。运行过程中
避免对同一航迹快照反复执行：

- `to_dict()`；
- 递归规范化；
- JSON 编码；
- SHA-256 计算。

稳定元数据只保存一次。航迹发布记录引用 `snapshot_revision` 和内容摘要。最终报告和离线
审计仍可展开完整字段。

### 减少对象复制

相机内参、传感器配置和来源信息使用只读共享对象。航迹未改变时复用上一版本的稳定字段，
只复制状态、协方差和其他动态字段。D2、D3 和 D5 读取只读航迹视图，避免各模块重复构造
完整数据传输对象。

第一轮目标是将持续处理速度提高到 3.5～5 帧/秒。

## D1 批量融合

D1 融合和扫描处理约占规则基线总墙钟的 74%，是首要优化对象。

### 两级关联门控

第一层使用位置网格或 k 维树进行低成本欧氏距离预筛选。第二层只对预筛选后的候选计算
马氏距离。

200 条量测与约 200 条航迹的完整组合最多包含 40,000 个候选。空间预筛选后，每条量测
只保留数个或十几个局部候选。

### 批量矩阵计算

将逐量测、逐航迹的 Python 循环改为数组计算：

1. 航迹状态组成 `N×6` 数组；
2. 航迹协方差组成 `N×6×6` 数组；
3. 预测量测和创新批量计算；
4. 先执行批量粗门控；
5. 对保留候选执行精确 Cholesky 求解和滤波更新；
6. 避免为每个候选创建临时 dataclass、字典和 JSON 对象。

粗门控可使用单精度浮点数，最终创新、协方差和状态更新继续使用双精度浮点数。

### 预测缓存

相同融合时刻下，每条航迹只预测一次。状态转移矩阵、过程噪声、预测量测、雅可比和创新
协方差按时刻及传感器类型缓存。同一批扫描复用计算结果。

D1 阶段目标是将候选数和创新求解数降低至少 60%，融合累计耗时降低 3～5 倍。

## 异步量测和历史重放

当前雷达、声学和光电量测包含不同延迟，乱序量测会触发固定滞后重放。

优化路径如下：

1. 按量测有效时间对同批扫描分组；
2. 同一融合周期只重放一次共享历史前缀；
3. 多条乱序量测合并后执行一次后缀传播；
4. 检查点只保存紧凑状态数组和版本引用；
5. 根据量测时间和检查点版本缓存预测结果；
6. 超出固定滞后窗口的量测继续失败关闭，不扩大重放范围。

优化必须保留 `measurement_timestamp`、`arrival_timestamp` 和当前乱序处理语义，不能通过
丢弃有效量测换取速度。

## D2 稀疏关联

D2 当前约占持续墙钟的 6%。D1 完成优化后，D2 可能成为新的主要瓶颈。

1. 使用空间网格生成局部候选；
2. 按候选图连通分量分别运行匈牙利算法；
3. 孤立航迹不进入代价矩阵；
4. 缓存每帧航迹投影和创新协方差；
5. 只对身份歧义分量启用有界多假设；
6. 保持 `id_switch_count`、航迹连续性和生命周期状态机不变。

该方案避免对每一帧构造全局稠密 200×200 关联矩阵。

## D5 和 D7 向量化

### D5 视觉配准

同一相机对全部航迹进行一次批量投影。相机内外参矩阵按帧缓存。边界框、射线、像素协方差
和重投影误差使用数组计算。先执行几何稀疏门控，再运行图神经网络或匈牙利匹配。

200 对 200 质点环境不生成 200 路光栅图像，只生成匿名局部航迹、像素位置和边界框历史。

### D7 比例导引

将全部分配对的相对位置、速度、视线角速率和导引加速度统一组成数组。完成批量计算后再
构造需要发布的命令对象。位置比例导引、视觉比例导引和现有切换门保持不变。

D3 当前耗时占比较低，继续使用稀疏候选边和 SciPy 匈牙利算法，不列入第一轮重点。

## CPU 并行策略

Core Ultra 9 185H 包含性能核和能效核，不适合直接创建大量 Python 线程。

建议采用以下配置：

1. main、D1 和 D2 优先运行在性能核；
2. JSON 写盘、D6 预处理和报告任务运行在能效核；
3. 独立传感器批次使用进程池，避免全局解释器锁限制；
4. 主进程按时间戳、传感器编号和扫描编号确定性合并结果；
5. 单 episode 首先测试 2～4 个工作进程，最多不超过 6 个；
6. 分别测试 NumPy、OpenBLAS 或 MKL 的 1、2、4、6 个内部线程；
7. 防止进程池与数学库线程叠加造成过度订阅。

跨进程传输使用共享内存数组或紧凑 NumPy 缓冲区，不反复 pickle 完整航迹对象。

## RTX 4050 使用范围

RTX 4050 6GB 优先用于：

- D5 图神经网络推理；
- 强化学习策略推理；
- YOLO 或视觉特征提取；
- 多相机大批量投影；
- 多 episode 批量粗门控对照。

暂不把单个 6×6 协方差求解直接搬到 GPU。单次 200×200 候选矩阵规模较小，数据传输和
内核启动时间可能抵消收益。

可采用 GPU 粗门控和 CPU 双精度确认的组合：

1. GPU 使用单精度浮点数计算批量距离和候选评分；
2. CPU 对少量候选执行双精度马氏距离和滤波更新；
3. GPU 超时、显存不足或结果非有限时回退 CPU 规则路径。

## 实施顺序

1. 延迟日志序列化和只读快照复用；
2. D1 空间预筛选和批量马氏门控；
3. D1 预测缓存和合并历史重放；
4. D2 连通分量稀疏匈牙利；
5. D7 和 D5 数组化；
6. 2～4 进程的传感器并行；
7. 最后评估 RTX 4050 的批量粗门控。

## 验收规则

每项性能优化必须同时满足：

1. 全部世界和航迹状态有限；
2. 在线真值使用次数为 0；
3. `global_track_id` 非法修改次数为 0；
4. 过时计划接受、重复分配和硬约束违规次数为 0；
5. D1、D2 最终航迹和 D3 分配没有未解释退化；
6. 相同随机种子的规范业务载荷等价；
7. 浮点运算顺序变化时，数值差异处于预设容差内且离散决策一致；
8. 不降低传感器、融合、关联、分配和导引频率；
9. 不删除协方差、双时间戳、来源谱系和必要审计字段。

## 阶段判断

完成日志延迟序列化、D1 空间预筛选和批量融合后，当前硬件达到 6～9 帧/秒是合理的阶段
目标。继续完成进程并行和局部本地内核后，目标可提高到 10～14 帧/秒。

在不降低任务频率和审计语义的条件下达到 20 帧/秒，可能需要将 D1 核心门控、历史重放和
滤波更新迁移到 Numba、C++ 或其他本地编译实现。
