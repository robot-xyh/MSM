# 版本对应与复现条件核查

核查日期：2026年9月26日。当前HEAD：`a0d3d8ad2cd037c71845119840dfd5cae426c2e6`。

## 一、核查结论

本轮覆盖原Goal关键材料及四份主要报告涉及的11类记录，包括正式450组、三批来源生成、远距离AirSim基线、双光电报告回放、搜索回放、旧中心交接、机间诊断选参、中心误差矩阵和三组AirSim接口代表试验。这不是对仓库全部历史输出逐一作出的复现保证。

目前最明确的是：已有多批结果可以继续核对保存计数和汇总表，但没有一批因本轮检查而获得“已原样复现”的结论。中心误差矩阵的材料相对完整，双光电报告回放也有源码指纹和输入清单；两者仍需区分质量结果与实测耗时，确认相关依赖后才能判断重运行的一致性。搜索回放的历史源码冻结不足。原正式450组缺少完整载荷，只能查阅摘要。

本轮没有启动仿真、加载模型、重新判定目标关系或重新评分。对已有计数的除法、求和和平均检查，不等于重跑算法。

## 二、判定方式

| 核查类别 | 本报告中的含义 |
| --- | --- |
| 原样运行条件 | 需要历史源码、未提交修改、完整配置、命令、输入、模型和环境记录；不能仅凭提交号判断 |
| 离线回放条件 | 保存观测或构造输入、冻结代码和模型、评分版本及参数能够对应；有候选材料不等于已经验证确定性 |
| 保存结果重汇总 | 直接使用已保存计数重算比值或合计，不重新运行检测、配准或其他算法 |
| 摘要查阅 | 只能引用原报告或聚合摘要，不能恢复逐组结果 |

完整登记见[REPRODUCIBILITY_REGISTER.csv](REPRODUCIBILITY_REGISTER.csv)。其中“不适用”用于来源生成目录等没有模型效果结果的对象，不能解释为试验失败。

## 四、源码版本核对发现

### 1. 双光电：提交号不足，但已保存文件指纹

[双光电复现清单](../../../research_modules/independent_experiments/dual_optical_online_benchmark/outputs/report_replay_20260819_v2/reproduction_manifest.json)记录提交`ad59ff3f…`，同时明确`worktree_dirty=true`。

其列出的5份源码与当前文件哈希全部一致。其中4份与该历史提交中的文件一致，但`report_matrix_replay.py`在该提交中不存在。因此，仅检出这个提交，不能得到当时的回放入口。现存入口可以通过已存哈希确认身份，不能反过来把它说成该提交自带的源码。

本轮只核对清单指定的源码，没有认定所有间接导入文件均已经冻结。原清单还说明旧360度理想单站输入构造会补入当时的默认字段；相关配置版本同样需要保留。

### 2. 搜索：记录了基线提交，没有完整冻结入口

[搜索复现清单](../../../research_modules/independent_experiments/center_terminal_cv_campaign/outputs/offline_search_100pct_cues_20260819/reproduction_manifest.json)也记录`ad59ff3f…`及脏工作区。其入口`exp_search/run_offline_matrix.py`不在该历史提交中，清单未提供该入口的历史哈希和完整源码快照。

现存代码能够说明当前实现，但不能在没有其他证据时认定与原运行代码完全相同。该批次的命令没有显式列出全部参数，对当时默认值也有依赖。

三组输入实际只有两种不同运动文件哈希。观测运动记录到0.8秒，其余17.2秒为外推。该事实来自保存清单，不是本轮重新计算运动轨迹所得。

### 3. 中心误差矩阵：有快照，仍不能只恢复提交

[源码快照索引](../../../research_modules/independent_experiments/center_terminal_cv_campaign/outputs/center_handover_sensor_error_20260820/source_snapshot/source_files.json)列出11份源码，另保存索引本身和工作区补丁，合计13项快照制品。清单对应的快照制品、模型及模型清单校验均匹配。

11份源码中，6份与记录的历史提交一致，3份在当时提交中有文件但内容不同，2份在该提交中不存在。当前11份文件均与保存的源码指纹一致。这说明快照确实补充了提交号未覆盖的内容，也说明仅恢复提交仍不完整。

快照范围、执行入口、输入构造和依赖仍需一起保留。模型只做文件哈希检查，本轮没有反序列化或运行模型。

### 4. 原三批来源配置能够对应

D3、D4、D5会话分别绑定`e7c438c…`、`6737b44…`、`64dfc08…`。每批的基础配置和调度文件，共6项，均与会话记录的哈希一致，也与对应历史提交中的文件一致。

这补充了来源配置的版本证据，但不改变上一轮的研究断点：来源完成并通过来源审计，不等于当前代际模型已经训练或通过评价。

逐文件比较见[SOURCE_VERSION_REGISTER.csv](SOURCE_VERSION_REGISTER.csv)。本轮27项带预期哈希的文件检查全部匹配，另对33项文件记录了当前指纹；后者没有历史预期值，不能称为“历史哈希通过”。

## 五、运行环境与确定性

当前Python为3.12.3，元数据查询得到NumPy 2.5.0、SciPy 1.17.1、PyTorch 2.11.0+cu128、Matplotlib 3.10.9、AirSim 1.8.1。所列核心包版本与相关保存记录一致；本轮查询没有导入PyTorch或启动GPU计算。

当前Linux内核为`7.0.0-34-generic`，历史环境记录为`7.0.0-28-generic`。现存`environment.json`主要记录版本信息，不是包含全部传递依赖及制品哈希的可安装锁定文件。仿真场景资产、系统调度、设备驱动和完整环境一致性也未由这些字段全部证明。

中心误差矩阵清单写有“deterministic CSV equality”，但`per_run_metrics.csv`保存了`runtime_s`，汇总也包含计时均值与分位数。该CSV与原记录哈希一致，只能证明当前保存文件未变；不能要求再次运行的实测耗时逐字节相同。

后续如仅做结果一致性核查，应先明确计数、质量指标、耗时及环境字段各自的比较规则。不得通过删除超时或低结果行使比较通过，也不应为了匹配旧哈希回填耗时。
