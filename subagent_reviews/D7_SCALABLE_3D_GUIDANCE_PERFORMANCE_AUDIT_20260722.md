# D7 三维导引性能波动审计

## 结论

clean 提交 `8f8619246298` 到 `f80b5bd42e2c` 的三 seed 汇总中，D7
`module.d7_guidance` 累计耗时均值由 `4.991960 s` 增至 `5.358198 s`，表面变化为
`+7.337%`。本次审计没有发现 D7 算法或计时路径的差异。该变化由 seed 42002 的一次
`+21.430%` 单点波动主导；另外两个 seed 合并后仅为 `+0.328%`。

两个提交的 D7 受控文件清单和 blob 完全相同。main 中包围 D7 的计时代码
`module_stack.py` 也使用同一 blob。三 seed 的调用次数、每次命令规模、逐帧命令、模式、
拒绝原因和规范化总线哈希均一致。冻结 200-pair 输入的平衡交错复测显示，同一份 D7
源码被人为标为“参考”和“候选”后，组均值仍可相差约 `6.58%`；12 次复测总体变异
系数为 `12.26%`。因此现有 `+7.337%` 只能记为未归因单机墙钟波动，不能记为 D7
性能回归。

本轮不修改位置比例导引、视觉比例导航制导、视线/预计碰撞时间滤波、`0.75 s` 航迹
陈旧门或 D3/D4/D5 安全门，也不实施其他 D7 优化。当前证据没有证明两个提交之间存在
可消除的非算法重复开销。

## 历史计时

`module.d7_guidance` 从 main 开始构造当前 assignment pair 输入时启动计时，覆盖：

1. main 查找 D2 航迹、D3 binding、D4 permission 和 D5 末端关联；
2. 构造 `AssignmentPairGuidanceInput3D`；
3. D7 `command_batch()` 和全部逐 pair 计算；
4. `GuidanceBatch3D.to_world_acceleration()` 数组复制。

计时在 D7 publication 构造之前结束。在线总线载荷生成和 JSONL 序列化不属于该阶段。
因此历史 `module.d7_guidance` 不是纯 D7 内核计时，不能直接据此修改导引公式。

| seed | `8f86192` / s | `f80b5bd` / s | 变化 | 调用数 | pair 总数 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 42000 | 4.885396 | 5.023875 | +2.834% | 185 / 185 | 36640 / 36640 |
| 42001 | 5.116725 | 5.011087 | -2.064% | 185 / 185 | 36544 / 36544 |
| 42002 | 4.973757 | 6.039633 | +21.430% | 185 / 185 | 36619 / 36619 |
| 三 seed 均值 | 4.991960 | 5.358198 | +7.337% | 185 / 185 | 逐 seed 一致 |

seed 42002 的候选运行虽然 D7 累计耗时最高，但整场核心墙钟由 `154.928 s` 降至
`147.297 s`，进程用户态时间由 `221.95 s` 降至 `193.28 s`。这不符合“D7 代码新增
稳定重复工作导致全局变慢”的特征。

## 冻结输入计时

复测固定 200 pair、每 trial 185 次调用、单核亲和性、固定 Python hash seed 和单线程
数值库。12 个 trial 按 `A-B-B-A` 顺序重复三轮；A、B 实际执行同一源码和同一冻结输入，
标签只用于估计测量噪声。

| 人工标签 | trial 数 | 均值 / s | 中位数 / s | 最小-最大 / s | 变异系数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| A（reference_blob） | 6 | 1.9404 | 1.9745 | 1.7101-2.1706 | 8.71% |
| B（candidate_blob） | 6 | 2.0681 | 2.1066 | 1.7169-2.4976 | 14.86% |
| 全部 | 12 | 2.0042 | - | 1.7101-2.4976 | 12.26% |

A、B 的人为均值差为 `+6.58%`，但两组运行的是同一份代码。12 次的命令数组、mode、
gate reason、首帧 200 次 `hold -> midcourse` 转换、末帧零转换和 200 个 pair snapshot
摘要均为
`7259425a8d711085512ae80876656e0fe08b0651c1be94464e8064dd7a464a3f`。
各 trial 的垃圾回收次数基本相同，无法把最大值归因于额外回收。剩余波动可能来自
调度、处理器频率、缓存和同机负载；现有证据不能进一步区分。

## 分配与序列化

冻结基准把不同边界分开计时：

| 操作 | 结果 | 是否在历史 D7 阶段内 |
| --- | ---: | --- |
| 200 个输入 DTO 构造 | 0.293 ms/batch | 是，但不含 main 的查找和 permission 扫描 |
| D7 冻结内核 | 9.244-13.500 ms/batch | 是 |
| 世界加速度数组复制 | 0.298 微秒/batch | 是 |
| publication 载荷物化 | 0.097 ms/batch | 否 |
| 约 64.2 kB JSON 序列化 | 0.499 ms/batch | 否 |

`tracemalloc` 单个冷启动 200-pair batch 的峰值为约 `826 kB`。主要存活分配来自 pair
状态、输出 dataclass、轨迹/协方差复制和命令 metadata。该测量会显著扰动墙钟，只用来
定位分配类别。两个历史提交执行同一分配代码，当前没有差分证据证明这些对象是本次
`+7.337%` 的来源。

## 处置

1. 将本次变化登记为“未归因单机墙钟波动”，不登记为算法回归或已关闭的性能优化。
2. 不修改 D7 核心代码、公式、阈值或安全门。
3. 后续正式性能试验应记录每次调用分布，而非只记录累计值；同一输入至少执行交错重复，
   同时记录 CPU 亲和性、频率策略、垃圾回收和同机负载。
4. 若后续需要优化输入准备，应由 main 单独计时 `_guidance_inputs`、D4 permission
   组装、D7 `command_batch`、世界数组复制和 publication，避免把 main 查找成本记到
   D7 算法名下。
5. 只有冻结输入显示稳定、可复现的差分，并在命令数组、mode、gate reason、pair state
   和状态迁移全部一致时，才允许提出小范围非算法优化。

## 证据边界

本报告使用 2026-07-22 已有的 clean-source 三 seed 输出和本机冻结输入复测。它不关闭
200 对实时 P1，不证明长期运行的 P95/P99，也不替代真实 AirSim 或未见 seed 验收。
冻结输入不包含 main 的完整 D4 permission 线性查找，因此不能用 9-14 ms 的内核时间
反推集成阶段应达到同一数值。
